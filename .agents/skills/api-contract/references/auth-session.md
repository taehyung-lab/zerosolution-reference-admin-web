# Auth transport and session incidents

Read this file only for token storage, refresh cookies, reissue, replay, 401/403, or cross-tab auth coordination. The rules below are what the code does; ADR 0006 owns why that was decided, what it excluded, and what is still unconfirmed.

- Store the access token through the approved try/catch adapter with an in-memory mirror; read it into `Authorization`.
- The login ID lives beside the access token with the same lifetime and the same adapter. It is not a secret — the sign-in request already carries it in plain text — and the reissue request body requires it, so a reload that keeps only the token cannot refresh. Clearing the token clears the login ID.
- The refresh token is an HttpOnly server cookie. The client guarantees only `withCredentials: true`; cookie name, expiry, SameSite, and response body remain server-contract inputs.
- Pre-auth paths (sign-in, 2FA, reissue) carry no `Authorization` header, and their 401 is a wrong credential rather than the end of a session: transport publishes no incident and clears nothing, and the screen that asked for the credential renders the failure in place through `resolveErrorOutcome('pre-auth', kind)`. Publishing it as a session fact turns a failed login into a redirect back to the login screen.
- HTTP 401 runs the contract's reissue endpoint once with the declared request body, stores the adapted token, and replays the original request once. The path and body come from the committed snapshot, never from a shortened guess.
- Transport declares the adapter shape only; the app boundary registers the reader that knows where the token sits in the declared response. Register it at module load of the auth boundary so a session restored without visiting the login screen can still refresh. An unregistered reader is a `contract` failure, not an auth failure.
- A document-local `refreshPromise` deduplicates concurrent failures. `navigator.locks` serializes cross-tab rotation and storage is rechecked after acquiring the lock.
- A replayed 401 may use a newer current token once without starting another reissue. Reissue never refreshes itself.
- A reissue failure is terminal only when the server refused the credential: the reissue response is 401/403, or its envelope declares a credential-rejection code. Which codes those are comes from the declared HTTP 200 `resultCode` table that `src/api/http/envelope.ts` holds, not from a guess about failure-sounding codes; every other declared failure keeps the kind that table gives it and the stored credential. A missing stored login ID is terminal too, because the declared request cannot be built. Network loss, timeout, and 5xx keep their original `kind` so the caller can retry — folding them into `unauthorized` throws the user out to the login screen whenever the server blinks.
- A 401 that survives the replay is terminal as well: the session is over, so the credential is cleared before the fact is published. A dead token left in storage lets the route guard admit the screen again and the next request repeats 401 → reissue → failure forever.
- A declared credential rejection also arrives on HTTP 200, because the envelope carries its own `resultCode`. The transport boundary that unwraps the envelope publishes that failure as terminal with source `api`; the pure unwrap function has no incident seam, so leaving it there classifies the failure as an incident that no boundary ever receives. Pre-auth envelopes are excluded exactly like their 401 counterparts, and every other declared code keeps the kind the table gives it and the stored credential.
- Terminal incidents distinguish `api`, `refresh`, and `cross-tab` sources and carry the credential generation that was alive when the failure happened. One publisher owns clear-then-publish for every terminal seam and reads that generation before clearing the credential. A second publisher splits the read order between seams and the consumer's suppression breaks again.
- The generation counts credentials that were established: storing a token increments it and clearing one does not. N concurrent 401s that each clear therefore still report the same generation, and a re-login raises it.
- A credential that reaches this document only through another tab's `storage` event is established too, so applying it raises the generation. Otherwise a tab that already required login for the previous generation stays suppressed forever once the new credential never passed through this document's own store. A `null` from that event is logout propagation and raises nothing.
- Transport publishes one unauthorized fact per failure and never deduplicates. The consumer owns suppression: once it has started requiring login for a generation, further facts for that same generation are ignored, and a newly stored credential lifts the suppression. Suppressing on the token string instead swallows every expiry after the first, because the credential is already cleared when the fact arrives. Without suppression at all, N concurrent 401s drive N navigations.
- Route entry into authenticated areas is guarded by the presence of a stored credential, not by its validity — only the server judges validity. The guard preserves the attempted location so the login screen can return there.
- HTTP 403 becomes an app incident only for an observed entry operation. Observerless prefetch has no loading or error surface.

Transport emits one-way incident facts; the app boundary owns UI and navigation. Never import app code back into transport.
