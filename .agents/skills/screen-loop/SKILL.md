# Screen Loop

요청의 크기를 가르고 필요한 근거를 읽어 설계·구현·검증한 뒤 실패 원인으로 돌아간다. **노드마다 파일을 만들지 않는다.** 일반 작업은 대화와 실제 diff·실행 결과로 수행한다. 기록이 필요한 드릴·감사만 [prepare/review 절차](../../../scripts/agents/README.md#prepare-before-editing)를 쓴다.

## 알갱이

| 요청 | 필요한 근거 | 구현 범위 |
| --- | --- | --- |
| **screen** — 화면 전체 | 구성·상태 실측, 동작·정책, 시작→입력→실행→실패·복구→다음 단계 | 해당 workflow와 실제 연결 |
| **slice** — 필터·이력·팝업 등 부분 | 부모의 관련 정책·상태 흐름과 해당 역할의 관찰·계약 | 요청한 부분과 필수 연결 |
| **component** | 실제 소비 위치·입력·상호작용·접근성, 공용인지 feature-local인지 | 컴포넌트와 소비 연결 |
| **logic** — 훅·유틸·mechanic | 실제 호출자, 입출력·소유권·전이·실패, 공용 여부 | 해당 책임과 직접 연결 |
| **structure** — 폴더·조립 | 실제 import·공개 경계·파일 책임과 배치 계약 | 필요한 파일 집합과 참조 수정 |

혼합 요청은 요구사항 ID 전체를 유지하고 검증 가능한 단위로 나눠 순차 진행한다. 마지막에 원래 요청 전체와 연결을 대조한다. 첫 조각만 끝내고 나머지를 지우지 않는다. 컴포넌트·로직·구조를 위해 가짜 화면 원장을 만들거나 화면 전체 절차를 적용하지 않는다.

## 그래프

| 노드 | 수행 | 다음 단계로 갈 근거 |
| --- | --- | --- |
| **N0 분류** | 크기·종류와 성공 조건 확인 | 범위와 요구사항 ID가 명확함 |
| **N1 진입** | 대상과 실제 소유자·소비자 탐색 | 근거와 편집 위치를 설명할 수 있음 |
| **N2 증거** | 필요한 원문·관찰·계약만 읽기 | 확인·미확인·충돌과 영향이 구별됨 |
| **N3 설계 선언** | 흐름·상태 소유·재사용·단순성 판단 공개 | 설계·요구사항·검증 방법이 연결됨 |
| **N4 구현** | 선택한 경계대로 작은 단위 구현 | 요구 동작과 필수 연결이 존재함 |
| **N5 검증** | 실제 결과와 공용화·소유권·복잡도 대조 | 요구사항별 실행 증거 또는 차단 조건이 있음 |
| **N6 판정** | 원래 요청 전체 완료 대조 | 미구현·차이를 숨기지 않고 필요한 독립 검토를 마침 |

N1–N2: 제품 근거는 [product.json](../../../docs/reference/product.json)의 `inventory` README·`index`·`judgment`·`scenarios`에서 **요청 대상**을 찾는다. 고정 도메인·대표 화면을 기준으로 읽지 않는다. `context`·`bundle`은 탐색 도구이며 호출 자체가 의무는 아니다. 색인에 없으면 실제 소유 파일·원문을 찾는다. 기존 코드의 존재와 제품 사실의 확인을 구별한다.

화면·부분 요청은 이미 분석된 관찰과 정책부터 읽는다. 필요한 구성·상태·수치가 없거나 오래됐으면 원문에서 실측한다. 현재 코드나 형제 화면으로 미확인 값을 채우지 않는다. 공용 후보는 이름이 아니라 현재 요구사항과 실제 소비 코드·계약·테스트로 판단한다. 소비자가 아직 없으면 첫 소비자를 구현해 적합성을 확인하고 검증 전 승격을 확정하지 않는다.

범위가 확인되면 AGENTS §2의 해당 SKILL을 읽고 현재 역할에 해당하는 reference 절만 추가로 읽는다. 파일 생성·이동은 folder-structure-contract, API는 api-contract, feature workflow는 feature-contract, 공용 UI·상태·유틸은 shared-ui-contract가 세부 기준을 소유한다. 전체 reference·과거 드릴 기록을 선로딩하지 않는다.

N3–N4: 관련 공용 계약을 `채택 / 수정 / 제외`하고 이유를 밝힌다. 요청한 역할만 구현하며 빈 역할 파일·wrapper를 관례 때문에 만들지 않는다. 기존 구조는 판단 입력이지 복사할 답지가 아니다. 직접 영향받는 payload/cache·navigation·권한·i18n·mock도 확인한다.

N5–N6: 변경에 맞는 기존 검사와 실측을 먼저 쓴다. 새 테스트는 중요한 동작·회귀가 기존 검사로 보호되지 않을 때 보완한다. 문서 문장·파일 존재를 확인하는 형식용 테스트를 만들지 않는다. 화면은 실제 렌더·상호작용, 로직은 경계 입력·전이·실패, 구조는 실제 import·조립·빌드를 확인한다. 정적 검사 통과를 제품 동작의 확인으로 보고하지 않는다. 게이트·루트·공용 계약 변경의 독립 검토는 [AGENTS §5](../../../AGENTS.md#5-실행협업-모델)를 따른다.

### 설계 선택

작은 수정에는 가짜 대안을 만들지 않는다. 경계·소유권을 바꾸면 현재 문제, 실질적 대안과 복잡도, 선택을 뒤집을 반례를 실제 소비자·코드·작은 실험으로 비교한다. 누가 무엇을 호출하는지, 어떤 값이 어디에 있는지, 어떤 책임을 공유하는지, 추가 구조가 어떤 비용을 줄이는지 설명한다. 일반 작업에 네 개 JSON 필드를 작성할 필요는 없다.

### N5 복귀

| 발견 | 복귀 |
| --- | --- |
| 요구사항·원문 누락이나 충돌 | N0 또는 N2 — 성공 조건·근거 수정 |
| 한 소비자 정책 때문에 공용 API 확대 | N3 — 경계 재판정, 근거 없으면 feature-local |
| Query·URL·Form·로컬 사이 같은 상태 복제 | N3 — 단일 소유자로 정리 |
| 불필요한 계층·wrapper·파일 | N3 — 책임을 단순하게 조립 |
| 올바른 설계인데 구현·연결 오류 | N4 — 원인 코드 수정 |
| 검사·실측이 요구사항을 관찰하지 못함 | N5 — 검증 방법 수정 |

같은 성공 조건으로 다시 검증한다. 요구사항을 지우거나 검사만 반복해 실패를 없애지 않는다. 새 변경·실패·미해결 우려가 없으면 종료한다.

## 실패 간선 — 실측된 것만

특정 파서·기록 절차의 E0–E8과 재현 이력은 [관찰 reference](references/observations.md)에 있다. 일반 구현에서 과거 실패 목록 전체를 읽지 않는다. 해당 실패가 발생했을 때 원인 소유자와 기록을 확인한다.

## 답지 대조

문서 루프 자체를 시험하는 **drill**에서만 [드릴 절차](references/drill.md)를 읽고 기록 절차를 시작한다. drill은 N3까지 대상 구현·정답 테스트를 닫고 **N4′ 답지 대조 → N5′ 차이 반영**을 수행한다. 일반 implement는 현재 코드·테스트를 읽고 수정한다. 다른 화면의 제품 값을 복사하지 않는다.

## 차이 라우팅 표

| 원인 | 고칠 곳 |
| --- | --- |
| 제품 근거 누락·충돌·오래된 관찰 | product.json이 연결한 해당 근거의 단일 소유자 |
| 구현·상태·조립 오류 | 실제 책임을 소유한 코드 |
| 반복 절차가 잘못되거나 모호 | 해당 skill/reference의 기존 절 |
| 검사가 잘못된 동작을 허용·차단 | 해당 기존 검사와 의미 있는 회귀 사례 |
| 일회성 분석·실측·인계 | 대화 또는 필요할 때만 임시 기록 |

먼저 기존 내용을 수정·통합·제거한다. 새 파일·규칙·검사기는 기존 소유자로 해결할 수 없는 반복 손실이 확인됐을 때만 추가한다. 모든 차이를 새 문서나 게이트로 바꾸지 않는다.

## 한계

일반 모드는 판단·실제 검증을 에이전트가 수행하며 hook이 선언·범위·독립 검토 기록을 자동 강제하지 않는다. 기록 모드는 기존 `prepare/review`가 범위·인용·변경 귀속·receipt를 검사하지만 제품 사실의 일치나 검토의 질을 증명하지 못한다. 기록 시작 이전 변경과 동시 세션의 귀속 한계는 [런타임 어댑터](../../../scripts/agents/runtime-adapters.md)를 따른다.

현재 제품에서의 성공, 스크립트 fixture 통과, 새 에이전트의 자율 구현, 실제 다른 제품 이관은 서로 다른 증거다. 확인하지 않은 범위를 완료로 확대하지 않는다.
