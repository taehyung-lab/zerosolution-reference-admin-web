# 0015. 문서 체계 — 두 질문 라우팅과 제품 사실의 단일 소유

- 상태: **잠정 채택** — 구조는 적용했고, 이것이 이전 체계보다 나은지는 같은 요구를 두 체계로 각각
  구현한 대조가 끝나기 전이다
- 날짜: 2026-09-17
- 결정자: 제품 소유자. 항목은 grilling 과 드릴 실측에서 확정했고 이 문서는 그 확정과 이유를 보존한다
- 관련: [0013](0013-agent-implementation-workflow.md)(게이트는 존재가 아니라 결과를 본다),
  [0014](0014-single-screen-shape.md)(역할별 책임 형태)

## 결정

**무엇을 읽을지는 요청의 종류가 아니라 두 질문이 정한다.** (1) 이 변경의 결과를 무엇으로 검증하는가,
(2) 제품 사실에 의존하는가. 그리고 **한 화면의 관찰·정책·미확인은 `product/facts/<ID>.md` 한 파일이
소유하고, 색인은 그 frontmatter 에서 생성한다.**

- 요청 문장의 크기는 기준이 아니다. 버튼 하나여도 결과가 렌더로만 판정되면 브라우저로 실측한다.
- 역할 계약을 고르는 것은 문서 이름이 아니라 fact 의 `role` 이다. 화면 이름과 문서 이름을 눈으로
  맞추지 않는다.
- 색인은 생성물이라 **틀린 채로 만들어질 수 없다.** 손으로 고치면 다음 생성에서 사라진다.

## 이유

이전 체계는 한 surface 의 사실을 inventory·judgment·scenarios·index 네 경로가 나눠 가졌고, 그 위치를
`docs/reference/product.json` 포인터가 가리켰다. 관찰 하나를 갱신하려면 세 곳을 고쳐야 했고, 실제로
세 곳이 어긋났다. 지금은 한 파일이다 — 측정된 유일한 개선은 **제품 사실 갱신 3 파일 → 1 파일**이다.

라우팅은 요청의 종류(screen·slice·component·logic·structure)로 갈랐다. 그 분류는 요청 문장의 크기를
기준으로 읽혔고, "버튼 하나"가 화면 계약을 건너뛰게 만들었다. 결과로 판정하면 그 갈림이 사라진다.

경로를 상수로 만들면서 포인터가 할 일이 없어졌다. 대상 제품도 같은 자리를 쓰므로 이관이 인용을
다시 쓸 것이 없고, 대상이 이미 쓴 fact 는 덮이지 않고 보존된다.

## 이 결정과 함께 켠 검사

문서를 바꿀 때마다 같은 손실이 반복됐기 때문에, 이 결정의 절반은 **검사**다.

| 검사 | 무엇을 잡는가 |
| --- | --- |
| `scripts/product/build-index.mjs` | fact frontmatter 의 필수 항목·id 불일치·중복·dangling `related`, 미이관 행이 가리키는 원장의 부재 |
| `evidencePreservationFailures` | 원장의 보호 열과 fact 의 `## 관찰·정책·미확인` 절이 사라지거나 비워지거나 관찰 표식이 지워지는 것 |
| `retiredDocumentNameFailures` | 은퇴한 문서·skill 이름이 살아 있는 문장에서 소유자로 지목되는 것 |
| `checkNegativeControlFailures` | 대조군 없는 검사가 등록되는 것 |
| `rootBudgetFailures` | 항상 로드되는 루트가 자라는 것 |
| `scripts/transition/port-audit.mjs` | 문서를 옮길 때 따라오지 않은 판단 |

`rootBudgetFailures` 의 상한은 **오늘의 크기이고 내려가기만 한다.** 루트는 162 → 50 → 172 → 209 로
두 번 자랐고 두 번 다 아무것도 잡지 않았다. 원인은 같다 — 문서 예산이 `notice` 였다.

## 이사 대조 결과 (전제 P1)

`port-audit` 로 옛 계약 29파일을 새 문서와 블록 단위로 대조했다. **그대로 복사한 문서는 손실 0,
손으로 다시 쓴 문서에서만 잃었다.** 143블록 → 회수·확인 후 50블록이 남았고, 각각의 처분은 이렇다.

| 처분 | 수 | 무엇 |
| --- | --- | --- |
| **회수** | 93 | 비화면 결과 판정 · 화면 조립 · 파일 workflow · 특수 화면 · 소유자 경계 · 의존 방향의 이유 · 승격 심사 · primitive 내부와 렌더 성능 · i18n · OpenAPI snapshot · locale 와 cache identity · 화면 근거를 읽는 순서 · 관찰표 · 독립 검토 · 문서 변경의 채택 조건 · 테스트 위치와 경계 · 한 feature 한 소유자 · 도구 출력의 빈 값 · 도달 가능한 진입점 |

| **C 이월** | 5 | 각 계약의 `name`·`description` frontmatter. 옮길 판단이 아니라 **런타임 라우팅의 재료**이며, skill 체계로 갈 때 재작성한다 |

## 버린 대안

- **포인터 파일로 제품 사실 위치를 선언** — 경로가 상수면 선언할 것이 없고, 선언은 어긋날 수 있다.
- **공용 카탈로그를 코드에서 생성** — 생성기가 읽을 수 있는 것은 export 목록이고, 카탈로그가 말하는
  것은 **무엇을 소유하고 무엇을 거절하는가**다. 그것은 코드에 없다.
- **인증·세션 계약을 transport 와 분리** — 재발급·만료·동시성은 transport 와 같은 실패를 공유한다.
  나누면 한쪽만 읽고 나머지 실패를 놓친다.
- **네 경로 원장을 유지한 채 색인만 생성** — 갱신이 여전히 세 곳이다.
- **fact 의 열거와 코드 enum 을 대조하는 게이트** — 오늘 **대조할 짝이 하나도 없다.** fact 5개 중
  어느 것도 코드 경로를 인용하지 않고, 구현된 feature 중 fact 를 가진 것이 없다. 짝이 없는 게이트는
  통과하면서 아무것도 잡지 않으며, 이 저장소는 그런 게이트를 세 번 만들었다([ADR 0013](0013-agent-implementation-workflow.md)).
  fact 가 `열거 ↔ 코드 심볼` 짝을 실제로 선언하게 되면 그때 만든다 — 그 전에는 만들지 않는다.

## 재검토 조건

- 같은 요구를 두 체계로 각각 구현한 대조에서 같은 질문·같은 예외·다른 화면 복사가 새 체계에서도
  나온다 — 그 문서 절로 돌아간다.
- 두 질문이 답을 주지 못하는 요청이 나온다 — 질문을 고치거나 셋째 질문을 만든다.
- fact 하나가 여러 화면을 담아야만 맞는 경우가 생긴다 — `role` 과 fact 단위를 다시 잰다.
- 루트가 상한에 걸렸는데 내릴 것이 없다 — 루트가 실제로 소유해야 하는 것이 무엇인지 다시 센다.

재검토는 투표가 아니라 실제 diff·focused test·브라우저 실측으로 판정한다.

## 이 결정이 답하지 않는 것

역할 계약을 런타임이 자동으로 발견하게 할 것인지(skill `description` 라우팅), 옛 원장 26화면을 언제
어떤 순서로 fact 로 옮길 것인지.

브라우저 실측은 **진입점과 상한까지** 스크립트가 답한다(`pnpm observe`) — 포트는 실행할 때 정해지고
상한은 실 API 연결 여부에 달려 있어 둘 다 문서에 적으면 낡기 때문이다. 무엇을 눌러 무엇을 보는지는
역할 계약의 `이 역할의 검증 대상` 이 소유하며, 그것은 판단이라 스크립트로 옮기지 않는다.
