# 0016. 역할 계약을 skill 로 올리고 라우팅을 런타임에 넘긴다

- 상태: **채택** — 라우팅 45/45 와 드릴 대조를 통과했다. 항상 로드되는 양이 늘어난 것은 알려진 대가다
- 날짜: 2026-09-17
- 관련: [0015](0015-document-system-two-questions.md)(두 질문 라우팅과 fact 단일 소유),
  [0013](0013-agent-implementation-workflow.md)(게이트는 존재가 아니라 결과를 본다)

## 결정

**역할·경계 계약 15개를 `.agents/skills/{name}/SKILL.md` 로 옮기고, 무엇을 읽을지는 각 skill 의
`description` 이 말한다.** 루트는 라우팅 목록을 세지 않는다. `.claude/skills` 는 `.agents/skills` 를
가리키는 **심링크**이지 복사본이 아니다 — 복사본은 정본과 어긋나고, 심링크는 어긋날 수 없다.

"발동하면 매번 필요한 것"은 `SKILL.md` 본문에, "만났을 때만 필요한 것"은 `references/` 에 둔다.

## 이유 — 관측된 것만

루트가 조용히 자랐다: 162 → 50 → 172 → 209. 원인의 절반은 **라우팅 지식의 집이 루트뿐**이라는
것이다. 예외가 생길 때마다 루트가 커지고, 조건부로만 필요한 문서를 둘 자리가 없어 루트로 올라온다.

옮기기 전에 전제를 쟀다. skill 하나와 심링크만으로:

| 무엇 | 결과 |
| --- | --- |
| 발견 | 새 세션이 `list-contract` 를 `description` 전문과 함께 목록에 갖는다 |
| 발동 | "운영자 목록에 상태 필터 추가" 요청의 **첫 tool call** 이 `Skill(list-contract)` |
| 비발동 | axios 봉투 · 날짜 유틸 요청은 열지 않고 각각 `api-wire` · `shared-ui` 로 갔다 |

옮긴 뒤 **45개 3종 평가**(skill 15 × 명백·재표현·비발동)를 실제 세션에 던졌다:
**45/45 통과, 비발동 15/15 통과.** 발동한 skill 수는 평균 1.64개, 최대 3개다.

같은 요청 셋을 옮기기 전 구조에서도 돌렸다. 차이는 줄 수가 아니라 **탐색 비용**이었다:

| 요청 | 파일 체계 | skill 체계 |
| --- | --- | --- |
| 목록 정렬 추가 | `ls product/` → `grep 회원` → `find src` (계약 문서를 끝내 열지 않음) | 첫 호출 `Skill(list-contract)` |
| business error 분류 | `ls contracts/*/` → `grep error api-wire.md` | 첫 호출 `Skill(api-wire)` |
| 훅 폴더 위치 | `grep '^#' source-structure.md` → `grep '^#' shared-ui.md` | 첫 호출 `Skill(source-structure)` |

파일 체계는 **어느 파일인지 찾는 데 매번 1~2회**를 쓰고, 찾은 뒤에도 절만 grep 해서 본다.

## 대가 — 항상 로드되는 양은 오히려 늘었다

| | 루트 | description 15개 | 항상 로드 |
| --- | --- | --- | --- |
| 파일 체계 | 7,631자 | — | **7,631자** |
| skill 체계 | 5,204자 | 5,854자 | **11,058자 (+45%)** |

루트 줄 수만 세면 205 → 153 으로 줄지만, `description` 은 공짜가 아니라 매 세션 로드된다.
**이 결정은 항상 로드되는 양을 줄이지 않는다.** 얻는 것은 탐색 비용 0과, 조건부 문서를 둘 자리다.

## 드릴 대조 — 같은 요구를 두 구조로 구현했다

`내정보 화면을 구현해주세요.` 한 문장을, 코드가 없는 화면(옛 원장 13번)에 대해 두 구조에서 같은
시각에 같은 기계로 돌렸다. 무개입이고 코디네이터도 없었다.

**결과 자체는 거의 같았다.** 폴더 배치·파일 집합·라우트·i18n·e2e 앵커가 수렴했다(32 vs 37 파일,
1,659 vs 1,667 insertions). 구조가 다르다고 다른 코드가 나오지는 않았다.

갈린 것은 둘이다.

**1. 계약에 이미 있던 문장을 읽었는가.** 두 구조의 폼 계약에 같은 줄이 있다 —
`blur 에서도 알려야 하는 불일치는 validators.onBlur 에 필드 하나만 더한다`. 원문도 비밀번호 확인
불일치를 blur 에서 알리라고 한다.

| | 한 일 |
| --- | --- |
| 파일 체계 | 그 줄을 쓰지 않고 제출 시점 검증으로 구현한 뒤, "공용을 한 소비자용으로 넓히지 않았다"고 fact 에 적었다. 결과는 **원문과 다른 화면**이다 |
| skill 체계 | `useSaveForm` 에 선택적 `blurValidator` seam 을 열고 카탈로그를 갱신했다. 훅은 값만 받고 필드의 의미를 모르며, 없으면 동작이 그대로다 |

파일 체계의 판단은 규칙으로는 옳게 들리지만, **그 규칙의 예외를 계약이 이미 적고 있었다.** 읽지
않은 것이지 넓히지 않은 것이 아니다.

**2. 원장을 정합하게 두었는가.** 두 구조 모두 GNB `내 정보` 를 `/profile` 로 이었다.

| | 남긴 상태 |
| --- | --- |
| 파일 체계 | `01-common.md` 는 여전히 "내 정보 클릭은 요청 로그까지 연결한다 … 내 정보 목적지는 미확정이다"라고 적고 있다. `context.json` 의 profile 은 `coverage: group`, `paths: []` 그대로다 — **거짓말하는 이정표 둘** |
| skill 체계 | 옛 문장을 지우지 않고 날짜 붙인 새 줄을 더해 확정 사실과 근거 포인터를 남겼고, surface 를 `group → surface` 로 좁히며 경로를 채웠다 |

양쪽 `pnpm verify` 통과(unit 945 vs **959**, e2e 123 동일).

**파일 체계가 이긴 것도 하나 있다.** 실측 보고가 더 구체적이었다 — 무엇을 열어 무엇을 눌렀고
무엇이 일어났는지를 전이별로 적었다. skill 체계는 상한만 말하고 누른 것을 열거하지 않았다.
루트가 요구하는 형식은 전자이므로, 이것은 `description` 이 아니라 **루트 rubric 이 덜 읽혔다**는
신호다.

## 버린 대안

- **루트 라우팅 표를 유지한 채 계약만 skill 로** — 같은 라우팅이 두 곳에 산다. 루트가 계속 자란다.
- **`.claude/skills` 에 복사본** — 정본과 어긋난다. 이 저장소는 그 어긋남을 이미 겪었다.
- **skill 을 더 잘게(카탈로그 단위로)** — 105쌍이던 겹침 검사가 폭증한다. 15개에서 비발동이 모두
  통과했으므로 더 쪼갤 근거가 없다.
- **`description` 을 요약으로** — 매칭 대상은 요청 문장이다. 요약은 문장과 겹치지 않는다.

## 재검토 조건

- 3종 평가에서 **비발동이 하나라도 깨진다** — 그것은 오탐이 아니라 잘못된 문서를 읽고 구현한다는
  뜻이다. 해당 `description` 을 고치고 다시 잰다. 고쳐지지 않으면 이 결정을 되돌린다.
- 루트가 예산을 넘는데 내릴 것이 없다 — 루트가 실제로 소유해야 하는 것을 다시 센다.
- 항상 로드되는 양이 문제로 관측된다(컨텍스트 압박·비용) — description 을 줄이거나 skill 을 합친다.
- 실측 보고에서 누른 것을 열거하지 않는 일이 반복된다 — 루트 rubric 이 읽히지 않는다는 뜻이므로
  그 자리를 다시 본다(드릴에서 한 번 관측됐다).

## 이 결정이 답하지 않는 것

Copilot 등 skill 을 자동 발동하지 않는 런타임에서의 라우팅(그 지시문은 "파일을 연다"로 남겼다),
`description` 이 바뀔 때 45개를 자동으로 다시 도는 시점.

## 어댑터가 링크라는 것은 검사가 지킨다

이관을 실제로 돌려 보니 **stage 가 링크를 따라가 22파일을 복제하고 있었다.** `stat` 이 심링크를
따라가기 때문이고, 그때 아무 검사도 울리지 않았다. 세 곳을 고쳤다 — manifest 는 `lstat` 으로 먼저
보고 링크면 링크 자체를 옮기며, stage·apply 는 `symlinkSync` 로 만들고, 해시는 가리키는 경로를
해시한다. stage 파일 수가 277 → 256 으로 줄었고 대상에 진짜 링크가 놓인다.

`skillAdapterFailures` 가 그 자리를 지킨다: 존재가 아니라 **무엇인지**를 본다(링크인가, 정본을
가리키는가). 대조군 5개. 이 검사는 켜자마자 또 하나를 잡았다 — `cpSync` 가 기본값에서 심링크를
절대경로로 바꿔 복사하고 있어, 저장소 사본의 어댑터가 **원본 체크아웃**을 가리키고 있었다.
