# 0016. 역할 계약의 정본을 skill로 둔다

- 상태: **채택**
- 날짜: 2026-09-17
- 관련: [0015](0015-document-system-two-questions.md)

## 결정

역할·경계 계약의 정본은 `.agents/skills/{name}/SKILL.md` 하나다. `description`은 발동 조건과 보내야
할 곳을 말하고, 루트는 skill 목록을 복제하지 않는다. 항상 필요한 판단은 본문에, 실제 상황을 만났을
때만 필요한 세부는 `references/`에 둔다.

런타임 연결은 정본을 복사하지 않는다. 런타임마다 자동 발견과 telemetry가 달라도 같은 요청에서 같은
계약을 선택하고 같은 관측 가능한 결과를 내는 것을 목표로 한다. 응답의 `requiredContracts`와 런타임이
실제로 로드한 `actuallyLoadedSkills`는 서로 다른 사실로 기록한다.

항상 로드되는 루트와 모든 description의 합계 상한은 내려가기만 한다. 상한에 걸리면 숫자를 올리지
않고 조건부 정보를 소유 계약으로 옮기거나 중복을 제거한다.

## 결정 당시의 관찰과 이유

라우팅 지식의 집이 루트뿐이었을 때 루트는 162 → 50 → 172 → 209줄로 다시 자랐다. 파일 체계에서는
목록 정렬과 훅 배치 요청이 계약을 찾는 데 검색 1~2회를 쓰거나 계약을 끝내 열지 않았다.

2026-09-17 Claude 환경에서 15개 skill에 명백·재표현·비발동 3종, 총 45개 요청을 실행했을 때
45/45가 기대와 일치했다. 같은 날의 구현 드릴에서는 파일 체계와 skill 체계의 코드 모양은 비슷했지만,
파일 체계가 이미 적힌 blur 계약을 읽지 않았고 제품 원장을 낡게 남겼다. 이 관찰은 당시 description과
Claude 환경에 대한 과거 사실이며 다른 런타임이나 이후 description의 통과를 주장하지 않는다.

당시 파일 체계는 항상 로드 7,631자, skill 체계는 루트 5,204자와 description 5,854자를 합쳐
11,058자였다. 탐색 비용을 줄였지만 고정 로드량이 45% 늘었다. 루트만 세는 예산으로는 이 대가가
보이지 않았기 때문에 둘을 합쳐 관리하기로 했다.

또한 이관 stage가 심링크를 따라 22파일을 복제했고, 복사 과정에서 절대경로 링크가 원본 checkout을
가리킨 일이 있었다. 복사본이나 런타임별 색인은 정본을 하나 더 만드는 선택이라 버렸다.

## 대가

- description은 모든 세션이 읽는 비용이다.
- 런타임별 자동 발견과 실제 로드 telemetry가 같지 않아 의미 선택과 로드를 따로 관찰해야 한다.
- 실제 에이전트 평가는 비싸므로 일반 코드 변경의 기본 검사가 될 수 없다.

## 버린 대안

- 루트 라우팅 표와 skill을 함께 유지: 같은 판단이 두 곳에 산다.
- 런타임별 계약 복사본이나 별도 색인: 정본이 갈라지고 어긋남을 사람이 관리하게 된다.
- 근거 없이 skill을 더 잘게 나누거나 합치기: 오발동·중복 소유가 실제로 관찰될 때만 경계를 바꾼다.
- 점수로 자동 채택·거절: 알려진 회귀 검사는 잡지만 새 변경의 대가와 런타임 차이를 판정으로 숨긴다.

## 재검토 조건

- 같은 의미의 요청에서 런타임별 `requiredContracts`가 반복해서 갈린다.
- 비발동 요청이 잘못된 계약을 선택하거나 계약을 지켰는데도 결과가 틀린다.
- 고정 로드량이 실제 context 압박이나 비용 문제로 관찰된다.
- 정본 하나를 유지하면서 새 런타임을 연결할 수 없다.

현재 검사 이름, 실행 명령, 런타임 지원 범위와 최신 관측은 코드·README·현재 baseline이 소유한다.
