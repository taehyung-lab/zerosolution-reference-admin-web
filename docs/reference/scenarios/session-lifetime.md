# 세션 만료·경고·연장 시나리오

세션 타이머는 이 저장소에 **미구현**이다(`.agents/skills/shared-ui-contract/references/incidents.md:8`). 이 카드는 그 작업의 설계 입력이며, 목적은 시나리오가 실제로 요구하는 것과 우리 공용 계약을 대조해 빠진 자리를 드러내는 것이다. 구현 코드는 여기서 쓰지 않는다.

증거 출처: 저장소 안은 `파일:줄`로 표기한다. 저장소 밖 관찰은 별도 세션 타이머 기준 구현의 설계·시나리오 가이드(2026-08-27 작성, 2026-08-26 브라우저 실측 포함)와 코디네이터가 확정한 실측 사실이며, 링크 없이 "외부 실측"으로 표기한다. `[확인]`은 파일:줄이나 스키마 원문으로 확인한 것, `[추론]`은 그 사실에서 끌어낸 판단이다.

## 1. 이 시나리오가 요구하는 것

Figma 상단 바는 모든 화면에 반복된다. 통합검색 input · **"로그아웃까지 남은시간 30:00 `연장`"** · 프로필 · `현장발권` · 알림 벨 순이다(`docs/reference/zero-sol/01-common.md:7`, 회원 도메인에서 같은 문장이 재관찰됨 `docs/reference/zero-sol/04-members.md:21`). `[확인]`

사용자가 보고 누르는 것은 네 가지다.

1. **상단 바 카운트다운** — `MM:SS` 형식으로 상시 노출. 30:00에서 시작한다. `[확인]`
2. **상단 바 `연장` 버튼** — 아무 때나 누를 수 있다. 성공하면 alert `1.1.3.3.1 세션 초기화`가 "세션 유지시간을 30분으로 초기화합니다." + `확인` 하나로 뜬다(`docs/reference/zero-sol/01-common.md:30`). `[확인]`
3. **만료 전 경고 팝업** — `1.4.4 팝업-세션종료 알림`. 작은 dialog이고 **상세 카피와 경고 시점은 미판독**이다(`docs/reference/zero-sol/01-common.md:14,37`). `[확인]`
4. **만료 후 종결** — Figma에 전용 frame이 없다. 현재 계약에서 종결의 표면은 `IncidentBoundary`다(`incidents.md:7`). `[추론]`

Notion에는 "세션: 5분0초부터 카운트 진행됨"이 있지만 이는 로그인·찾기·마케팅의 인증코드 카운터 문맥이다(`docs/reference/zero-sol/01-common.md:42`). 세션 경고 임계로 쓰지 않는다. `[추론]`

## 2. 상태와 전이

### 2.1 우리 계약이 선언한 값

스냅샷 `openapi/admin.snapshot.json:5`(`info.description` 원문)가 선언한 것. `[확인]`

- `Access Token 30분, Refresh Token 7일` — 웹 기준. 단, 같은 절이 `refreshToken`·`isLoggedIn`을 **MaxAge 미설정 세션 쿠키**라고도 선언한다. "7일"과 "브라우저 종료 시 삭제"는 같은 문서 안에서 서로 다른 수명을 말한다.
- `X-Session-Expires` — ISO-8601 응답 헤더. "세션 만료 시점. **매 요청마다 30분 후로 갱신 (슬라이딩)**. 30분 비활동 시 세션 만료 → `SESSION_EXPIRED(4004)` 응답".
- PING: `POST /api/v1/auth/ping`, "클릭·키보드 입력 등 UI 활동 감지 시", "1분 throttle". 서버는 Redis 세션 TTL을 30분으로 갱신한다(`openapi/admin.snapshot.json:6985-7006`).

인증 태그 4개 엔드포인트의 실제 스키마. `[확인]`

| 엔드포인트 | 요청 | 응답 | 근거 |
| --- | --- | --- | --- |
| `POST /api/v1/auth/ping` | 없음 (body·parameter 모두 없음) | `rs.Ja.Void` | `:6985-7006` |
| `POST /api/v1/auth/reissue` | cookie `refreshToken`(optional) + body `ah.AuthDTO$ReissueRequest`, `security: []` | `rs.Ah.AuthDTO$SignInResponse` | `:6942-6984` |
| `POST /api/v1/auth/sign-out` | 없음 | `rs.Ja.Void` | `:6887-6908` |
| `PUT /api/v1/auth/password` | body `ah.AuthDTO$ChangePassword` | `rs.Ja.Void` | `:3093-3123` |

**연장의 성공 신호는 응답 본문에 없다.** `ping`도 `password`도 `rs.Ja.Void`를 돌려준다. 새 마감 시각은 오직 `X-Session-Expires` 헤더에만 있다. `[확인]`

### 2.2 access token 만료와 세션 만료는 다른 것이다 `[추론]`

우리 계약 기준으로 **다르다**. 근거는 두 개가 서로 다른 실패 표면과 서로 다른 복구 경로를 갖는다는 것이다.

- **access token 만료** = JWT `exp`. 표면은 HTTP 401이고, 복구는 `reissue` 1회 + 원 요청 replay 1회로 **사용자에게 보이지 않게** 끝난다(`auth-session.md:8,11`). 서버가 자격증명을 거부했을 때만 terminal이다(`auth-session.md:12`).
- **세션 만료** = 서버 Redis TTL. 표면은 `X-Session-Expires`가 광고한 절대시각과, 스냅샷 산문이 말하는 `SESSION_EXPIRED(4004)`다. 복구는 없고 사용자에게 보인다.

둘의 선언 길이가 **똑같이 30분**이라는 점이 위험하다. 정상 흐름에서는 구분이 관측되지 않다가 어느 한쪽 정책이 바뀌는 순간에만 드러난다. 이 때문에 401을 세션 만료로 접거나 remaining으로 401 종결을 막는 코드가 살아남기 쉽다. 둘 다 외부에서 실제 사고로 지불된 형태다(§3).

### 2.3 상태 집합

```text
none ──로그인 응답 헤더──▶ live ──remaining<=경고임계──▶ warning ──remaining<=0──▶ expired
                            ▲                              │
                            └────── 새 X-Session-Expires ───┘
```

- **시간으로 진행하는 것은 하나뿐이다**: `remaining = deadlineAt - now`. `live → warning → expired` 전이는 전부 이 파생값이다. 저장된 `warningShown` 같은 플래그를 만들지 않는다.
- **서버 응답으로만 바뀌는 것**: `deadlineAt`. 값의 출처는 응답 헤더 하나뿐이다. HTTP 200이라는 사실만으로 시간을 더하지 않는다.
- **이 축 위에 있지 않은 것**: 401 → reissue. 이것은 transport가 소유하는 별도 축이고 세션 상태를 바꾸지 않는다. 반대로 reissue가 terminal이면 remaining과 무관하게 종결한다(`auth-session.md:12-13`).

## 4. 처음부터 알았다면 이렇게 설계한다

### 4.1 롤링 TTL: 마감의 권위를 무엇으로 좁히는가

문제의 핵심은 **서버가 강제하는 마감**과 **제품이 원하는 마감**이 다르다는 것이다.

- 서버가 강제하는 것 = `마지막 인증 요청 + 30분`. 스냅샷 선언이다 `[확인]`.
- 제품이 원하는 것 = `마지막 **사용자 활동** + 30분`. **이것은 아직 제품 정책이 아니다**(미확인 5). 아래 2·3은 유휴 로그아웃이 정책으로 확정된 경우에만 성립하며, 정책이 "서버 TTL 그대로"면 2는 불필요해지고 요청 억제도 도입하지 않는다 `[추론]`.

이 둘은 클라이언트가 사용자 의도 없는 인증 요청을 보내지 않을 때에만 같아진다. 그러므로 **마감 권위를 좁히는 자리는 타이머가 아니라 요청을 내보내는 쪽이다.** `[추론]`

1. **표시 권위는 서버가 준 절대시각 하나다.** `deadlineAt`은 오직 `X-Session-Expires`에서만 온다. HTTP 200, 로컬 30분 가산, 클라이언트가 계산한 어떤 시각도 권위가 아니다. 클라이언트 시계는 그 절대시각을 **가리키는 커서**일 뿐이다.
2. **전진 권위는 사용자 의도가 있는 요청으로 좁힌다.** 배경 트래픽(폴링, 미관측 prefetch, 유휴 상태의 자동 refetch)은 **유휴일 때 나가지 않아야** 한다. 나가면 서버 TTL은 밀리는데 제품 정책은 유휴 로그아웃이라 두 시계가 갈라지고, 그 응답의 헤더가 경고 UI를 자기가 닫는다.
3. **그럼에도 갈라지는 잔차는 서버 편으로 접는다.** 우리가 못 막은 요청이 마감을 밀었다면 표시도 밀린다. 클라이언트가 서버보다 짧은 마감을 임의로 유지하면 "만료됐다고 말했는데 API는 살아 있는" 반대편 좀비가 된다.

즉 **서버 deadline 타이머는 사용자 유휴를 증명하지 못한다.** 그 타이머가 세는 것은 마지막 인증 요청부터의 시간이지 마지막 사용자 활동부터의 시간이 아니다. 책임은 셋으로 갈린다. **UI 활동 측정**(무엇을 활동으로 볼지)과 **요청 억제**(유휴일 때 무엇을 안 내보낼지)는 서로 다른 자리이고, **타이머**는 그 둘의 결과로 서버가 광고한 마감을 표시할 뿐이다. 다시 말하지만 뒤의 둘은 유휴 로그아웃이 정책일 때만 필요하다.

### 4.2 시각의 진실: 서버 시각 `[추론]`

`deadlineAt`은 서버가 만든 절대 instant다. 클라이언트가 갖는 것은 tick뿐이다. 두 시계가 어긋나면 표시가 틀린다.

- 최소 형태: 헤더를 받은 순간의 `Date.now()`를 함께 저장하고, remaining을 `(deadlineAt - 수신시각) - 경과`로 만든다. **이 식은 로컬 시계 오차를 우회하지 못한다.** 수신시각 자체가 로컬 벽시계라, 시계가 δ만큼 틀려 있으면 첫 remaining도 δ만큼 틀린다. 이 식이 실제로 지키는 것은 그보다 좁다: **수신 이후의 경과를 단조 시계로 재면 카운트다운 도중의 시계 조정(NTP 스텝, 절전 복귀, DST)이 표시에 누적되지 않는다.**
- 그 남은 오차는 표시만 틀리게 하지 않는다. §2.3에서 `expired`는 `remaining<=0`의 파생이므로, 앞선 시계는 서버 세션이 살아 있는데도 만료를 주장할 수 있다. §3의 좀비 세션(시간이 인증 거부를 이기려 한 사례)과 방향만 반대인 같은 결함이다. 종결의 권위를 시계에만 두지 않는 근거이며, 임계 판정은 미확인 3·4가 답한 뒤 정한다. `[추론]`
- 정밀 보정(응답 `Date` 헤더로 offset 관측)은 처음부터 만들지 않는다. 외부 실측에서 그 offset은 RTT와 HTTP `Date`의 1초 해상도 때문에 구조적 음수 편향을 갖고, 작은 음수만으로는 시계 오차를 판정할 수 없었다. 서버 시계 편차가 실제 결함으로 관측되기 전에는 비용만 남는다.
- 표시는 duration(`MM:SS`)이므로 timezone과 무관하다. `displayTimeZone()`(`src/shared/lib/datetime.ts:8`)을 끌어들이지 않는다.

### 4.3 탭이 여럿일 때: 무엇이 필요하고 무엇이 과잉인가 `[추론]`

**필요한 것 하나** — 모든 탭이 같은 `deadlineAt`으로 수렴하는 것. 어느 탭이 연장하든 다른 탭의 배지가 따라와야 한다.

**과잉인 것** — master election, heartbeat, stale 임계 2종, `warningOwner` lease, BroadcastChannel 메시지 taxonomy, popup 액션 봉투, Web Worker clock. 이것들은 전부 **"별도 OS 창 하나"라는 전역 단일 자원**을 UI로 고른 대가다. 그 창은 origin에 하나뿐이라 소유자를 정해야 하고, 소유자를 정하면 소유자의 죽음을 감지해야 하고, heartbeat가 필요하고, 경고 60초를 잃지 않으려면 일반 stale과 다른 임계가 또 필요해진다. Figma는 별도 창을 요구하지 않는다. **탭 안 dialog로 그리면 이 사슬 전체가 사라진다.**

탭 간 수렴은 이미 있는 수단으로 충분하다. 자격증명이 이미 `localStorage` + `storage` 이벤트로 탭 간 동기화되고 있다(`src/api/http/incident.ts:50-58`). 같은 어댑터에 마감 시각을 쓰고 같은 리스너에서 읽으면 새 채널이 필요 없다.

두 탭이 동시에 `연장`을 눌러 ping이 2회 나가는 것은 **결함이 아니다**. ping은 멱등이지만 두 응답이 같은 마감을 주지는 **않는다**. 롤링 TTL이므로 각 응답은 자기 요청이 처리된 시점 기준 30분이고(`openapi/admin.snapshot.json:5`), 두 값은 몇 밀리초~수백 밀리초 차이가 난다. 그래도 election은 필요 없다. 두 값 모두 전진 방향이고, 어느 쪽이 남아도 사용자가 보는 것은 "방금 연장됐다"이며, 아래 채택 규칙이 더 나중 것을 남긴다. 비용은 요청 1건이지 정합성이 아니다. `[추론]`

늦게 도착한 응답이 최신 마감을 되돌리는 문제(§3)만은 남는다. 해법의 방향은 election이 아니라 **각 표본에 요청 발신 시각을 붙여 채택 순서를 정하는 것**이지만, 그 한계를 분명히 해야 한다. **클라이언트가 붙인 발신 시각은 서버 처리 순서를 증명하지 못한다.** 병렬 요청에서 먼저 보낸 요청이 서버에서 나중에 처리될 수 있고, 롤링 TTL의 마감은 **처리 시점**에 정해진다. 즉 발신 시각 채택은 "도착 순서로 인과를 대신하는" 명백한 오류만 제거할 뿐, 정당한 마감 단축과 늦게 온 옛 응답을 **둘 다** 올바르게 가르지는 못한다. 그것을 가르려면 표본마다 서버가 붙인 순서 근거가 필요하다(미확인 8). 그 근거가 없는 동안에는 발신 시각을 최선의 근사로 쓰고, 최댓값만 채택하는 규칙은 쓰지 않는다. `[추론]`

### 4.4 어느 레이어에 붙나 `[추론]`

AGENTS.md §3의 상태 소유권 표에서 "인증·권한·locale·timezone 같은 앱 수명주기"는 app boundary/provider가 단일 소유자다. 세션 마감은 그 범주다. `shared/`는 서버 계약을 알 수 없으므로 소유할 수 없고, `features/`에는 소비자가 없다.

## 6. 미확인

답이 없으면 구현이 갈리는 것만 적는다.

1. **서버가 세션 만료 시각을 어떤 형태로 알려주는가.** `[확인]` 스냅샷은 `X-Session-Expires`(ISO-8601)를 **응답 헤더**로, `info.description`과 `sign-in`·`ping` 엔드포인트 설명의 **산문**으로만 선언한다(`openapi/admin.snapshot.json:5,6915,6991`). 스냅샷 전체에 OpenAPI `responses.headers` 선언은 **0건**이고, `ping`·`sign-out`·`password`의 200 본문은 모두 `rs.Ja.Void`다. 따라서 **응답 본문에 만료 필드는 없고, 생성물이 타입으로 보증하는 헤더도 없다.** 이 헤더를 읽는 코드는 계약이 아니라 산문에 의존한다. 신규 백엔드 계약에서 이 헤더를 스키마로 선언받지 못하면, 그 사실을 코드 한 곳에 고립시키고 `contract` 실패로 다룰지 결정해야 한다.
2. **cross-origin 배포에서 `X-Session-Expires`가 CORS로 노출되는가.** 배포 환경 자체가 미확인이다(`AGENTS.md` §1). 노출되지 않으면 헤더는 존재해도 읽히지 않고, 이 설계 전체의 권위가 사라진다. 대안(응답 본문 필드)은 신규 계약 협상 대상이다.
3. **측정된 access token TTL과 선언값 30분 중 무엇이 배포 사실인가.** 불일치가 보고됐다(§3). access token TTL, 서버 세션 TTL, refresh cookie 수명 셋이 서로 어떤 관계여야 하는지 확정되기 전에는 "만료 전 경고"의 시점을 정할 수 없다.
4. **경고 임계값.** Figma `1.4.4`가 미판독이고 Notion의 "5분0초"는 인증코드 카운터 문맥이다. 5분(상단 바 색 변화 시점 후보)인지 1분인지에 따라 사용자가 반응할 시간과 dialog 카피가 달라진다.
5. **유휴 로그아웃이 제품 정책인가.** 롤링 TTL 아래에서 "유휴 30분 후 로그아웃"을 지키려면 유휴 중 배경 인증 요청을 금지해야 하고, 이는 자동 갱신이 필요한 화면(대시보드·발권 현황 등)의 요구와 정면으로 충돌한다. 정책이 확정되기 전에는 폴링을 도입하지 않는다.
6. **`PUT /api/v1/auth/password`의 "및 연장"이 세션 연장을 뜻하는가.** summary가 "09. 비밀번호 변경 및 연장"이지만 description이 없고 응답은 `rs.Ja.Void`다(`openapi/admin.snapshot.json:3093-3123`). 비밀번호 **유효기간** 연장인지 **세션** 연장인지 스키마만으로 판정할 수 없다. 세션 연장이라면 `ping` 외에 두 번째 연장 진입점이 생긴다.
7. **`SESSION_EXPIRED(4004)`가 어떤 HTTP status와 봉투로 오는가.** kind 매핑 자체는 이미 `unauthorized`로 선언·구현돼 있다(§5). 남은 갈림은 status다. 401로 오면 `client.ts`의 재발급 인터셉터를 촉발해 세션 만료가 토큰 재발급 경로로 잘못 흘러들고, HTTP 200 봉투로 오면 그 경로를 타지 않는다. 이 값이 확정되기 전에는 4004를 별도 kind로 승격하지 않는다.
8. **병렬 응답의 마감을 무엇으로 정렬하는가.** 발생: 두 탭 동시 `연장`, 또는 요청이 겹치는 화면. 클라이언트 발신 시각은 서버 처리 순서를 증명하지 못하므로(4.3), 정당한 마감 단축과 늦게 온 옛 응답을 모두 올바르게 다루려면 서버가 표본마다 순서 근거를 줘야 한다. 후보는 셋이고 요구 강도가 다르다. **세션 sequence**(단조 증가 정수, 정렬만으로 해결), **마감 발급 시각**(서버 시각의 절대 instant, 정렬 가능하고 4.2의 offset 관측에도 쓰인다), **명시 TTL**(`남은 초`. 정렬 근거가 못 되므로 셋 중 가장 약하다). 답이 없으면 발신 시각 근사를 유지하고, 답이 오면 채택 규칙이 근사에서 증명으로 바뀐다.
