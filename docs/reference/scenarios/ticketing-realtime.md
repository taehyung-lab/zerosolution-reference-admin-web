# 시나리오 카드 — 발권 실시간

이 저장소의 공용 UI·상태·API 계약이 **실시간 사실을 소비하는 화면**을 감당하는지 대조하는 카드다.
인벤토리(`zero-sol/`)는 관찰만 기록하지만 이 카드는 4·5절에서 판정을 낸다. 그게 다른 점이다.

표기: `[관측]` 2026-08-11~08-19 개발 환경 브라우저 콘솔·DevTools WebSocket 프레임 원문과 화면 캡처.
`[선언]` 이 저장소의 파일에 실제로 있는 문장. `[추론]` 둘에서 끌어낸 판단. `[미확인]` 6절.
프레임 원문은 격리된 리허설 계약과 같은 계열의 관측이며 신규 서버 계약의 진실이 아니다.

## 1. 이 시나리오가 요구하는 것

운영자는 목록에서 예매 행 N개를 고르고, 프린터를 지정하고, 미리보기 후 발권을 실행한다.
실행 이후 화면은 세 가지만 답하면 된다. **지금 프린터가 무엇을 하나 / 내가 고른 표는 어디까지 나왔나 /
다음에 무엇을 해야 하나(재시작·취소·닫기).** 프레임 원문을 그대로 노출하는 화면이 아니다.

이 화면은 목록도 폼도 아니다. 목록 위에서 **되돌릴 수 없는 물리 출력**을 실행하고, 그 결과가
요청의 응답이 아니라 별도 채널로 나중에 도착한다. 인벤토리도 이 화면을 "list가 아닌 화면 유형"으로
따로 묶었다([06-ticketing.md](../zero-sol/06-ticketing.md):22) `[선언]`.

**작업 축과 티켓 축을 왜 나눠야 하나.** 두 사실은 수명이 다르다.

- **티켓 축** — "이 티켓은 발권됐는가." 서버가 소유하는 영속 사실. 재발권 방어, 분실 처리, 카드 중복
  판단의 근거다. 화면을 닫아도 남는다.
- **작업 축** — "이번 작업에서 이 행은 지금 어떤가." 발권대기·발권중·중단. 화면 수명만큼만 산다.

한 컬럼에 합치면 작업이 중단될 때 "발권중단"이 원래의 "발권완료"를 덮어 재발권 방어가 사라진다
(3절 F1). 서버 계약도 이미 두 축을 분리해 선언한다. `TicketStatusType`은 `AWAITING|COMPLETED|LOST`
([admin.snapshot.json](../../../openapi/admin.snapshot.json):20134), `IssuanceJobStatusType`은
`PRINTING|DONE|ERROR|CANCELLED`(:20666)로 **교집합이 하나도 없다** `[선언]`.

**REST 200은 발권 완료가 아니다.** `issuance/start`·`cancel`·`restart`는 요청 수락만 답한다(:4146 등).
행이 실제로 나왔다는 직접 증거는 실시간 완료 프레임뿐이다 `[관측]`.

## 2. 상태와 전이

축이 셋이고, 화면이 그리는 행 상태는 네 번째 파생물이다.

| 축 | 값 | 출처 |
| --- | --- | --- |
| 프린터 | `IDLE` `PRINTING` `ERROR` `CANCELLED` `DONE` | 실시간 STATUS 프레임 `[관측]`. 같은 5값이 REST `GET /printers/connected`의 `printStatusType`으로도 선언됨(:21958) `[선언]` |
| 작업(job) | `PRINTING` `DONE` `ERROR` `CANCELLED` | REST 선언(:20666). **`IDLE`이 없다** `[선언]` |
| 티켓 | `AWAITING` `COMPLETED` `LOST` | REST 선언(:20134). `AWAITING`은 실출력 시작 시 선제 생성되고 `DELETE issuance/awaiting`으로 해제된다 `[선언]` |
| 행 표시(파생) | 발권대기 · 발권중 · 발권완료 · 발권중단 · 확인요망 | 위 셋 + 프레임의 `reservationId`로 화면이 파생 `[추론]` |

```text
발권 실행(REST 수락, jobId 확보)
  → STATUS PRINTING(reservationId=r, job=j)      ← 이 행이 인쇄 시작됨
  → ISSUING(r, ticketId)                          ← 물리 완료 아님. ticketId가 이미 실려 온다
  → ISSUED(r, ticketId, job=j)                    ← 이 행의 유일한 직접 완료 증거
  → (다음 행 PRINTING …) → STATUS DONE(j) → STATUS IDLE(null/null)

분기 ERROR(errorCode) ─ 재시작 → 같은 job으로 PRINTING 재개 → 남은 행 ISSUED
                      └ 취소   → CANCELLED(reservationId=null) → IDLE(null/null)
```

`IDLE`은 한 값이 아니라 **세 형태**로 온다 `[관측]`.

| 형태 | printedCount / totalCount | issuanceJobId | 뜻 |
| --- | --- | --- | --- |
| ① 최초 접속·유휴 | `0` / `0` | `null` | 잔업 없음 |
| ② 종결 직후 자발 IDLE | `null` / `null` | `null` | 잔업 해제됨 |
| ③ ERROR 중 상태확인 응답 IDLE | 양수 / 양수 | **유지** | **잔업 보유. 여기서 같은 job이 재개된다** |

**무엇이 REST로 오고 무엇이 실시간으로 오나.**

| 사실 | 채널 |
| --- | --- |
| 발권 대상 행과 원래 티켓 상태, 프린터 목록 | REST `[선언]` |
| 작업 착수 수락과 `issuanceJobId` | REST `[선언]` |
| 프린터가 지금 무엇을 하나, 진행 카운트 | 실시간 STATUS `[관측]` |
| 어느 행이 인쇄 시작됐나 | 실시간 STATUS `reservationId` (PRINTING일 때만 값) `[관측]` |
| **어느 행이 완료됐나** | 실시간 ISSUED **뿐**. 스냅샷의 어떤 스키마에도 `ISSUING`/`ISSUED`가 없다 `[선언]` |
| 연결 유실 후 무엇이 진실인가 | REST `GET /ticket-registers/issuance/{issuanceJobId}/status` — 설명이 그대로 "WebSocket 재연결 시 유실된 발권 상태 복구"이고 예매별 `ticketStatus` 스냅샷을 준다(:8126) `[선언]` |
| 미리보기 이미지 | 실시간 preview 채널(프린터별 유일 토픽) `[관측]` |
| 인쇄 완료·취소·카트리지 알림 | SSE(별도 채널, `/api/v1/notifications/subscribe` :10749) `[선언]` |

## 3. 관측된 실패

| 무엇이 깨졌나 | 왜 그렇게 됐나 | 애초에 무엇을 몰라서 |
| --- | --- | --- |
| **F1** 한 행에 초록 `발권완료`와 빨강 `발권중단` 배지가 병기됨. 중단이 완료를 가려 재발권 방어가 사라짐 | 작업 상태와 티켓 상태를 한 컬럼에 렌더 | 두 축의 수명이 다르다는 것(영속 vs 화면 수명) |
| **F2** 종결 후에도 발권 세션이 남아 검색·초기화 뒤에도 임시 배지가 유지됨 | 세션 종결을 `printStatus`만으로 판정 | `IDLE`이 세 형태이고 그중 하나는 잔업을 보유한다는 것 |
| **F3** 잔업 IDLE에서 세션을 폐기해, 재개된 인쇄 프레임의 귀속이 사라짐 | `IDLE` = 유휴로 해석 | `IDLE`(잔업 유지) 상태에서 **같은 jobId로 `PRINTING`이 재개**된다는 것. 실측: `IDLE(11/222, job 409)` → 같은 job 409로 PRINTING 재개 → 연속 ISSUED |
| **F4** 사용자가 누른 취소가 앞선 오류 문구에 덮여 '카드 오류'로 오인됨 | 처음 본 오류를 유지하고 최신 프레임으로 수렴시키지 않음 | 취소 요청 뒤에도 `ERROR`가 먼저, `CANCELLED`가 나중에 온다는 것 |
| **F5** 카운트로 완료·실패를 추정해 엉뚱한 행이 실패 표기됨 | `printedCount`/`totalCount`를 진행 인덱스로 사용 | 종결 프레임에서 두 값의 의미가 흔들린다는 것. 실측: `CANCELLED`에서 `printedCount 24 > totalCount 20` |
| **F6** 같은 오류 안내·정산이 2~3회 중복됨 | 프레임 수신을 이벤트로 누적 | 동일 `ERROR` 프레임이 연속 반복 도착한다는 것(여러 트레이스에서 재확인) |
| **F7** 다른 프린터·다른 운영자의 프레임이 내 행을 바꿈 | SN·타이밍·인덱스로 귀속 추정 | status·issue가 프린터별이 아닌 **공용 브로드캐스트 토픽**이라는 것 |
| **F8** 타이머로 실패를 확정해 실제로는 나온 표를 실패로 표기 | 늦은 완료 프레임이 없다고 가정 | 오류·재시작 후 `ISSUED`가 수십 초(약 49초 관측) 뒤 도착할 수 있다는 것 |
| **F9** 연결 단절 구간의 특정 행을 실패로 표기 | 프레임 부재를 실패로 해석 | 단절 중 실제 출력 여부는 프레임으로 알 수 없고 REST 스냅샷으로만 복구된다는 것 |
| **F10** 화면에 `대기 (0/null)`이 그대로 노출됨 | 프레임 원문을 그대로 echo | `null` 카운트가 '잔업 해제'라는 종결 신호이지 표시값이 아니라는 것 |
| **F11** 프레임 판별 규약이 채널마다 달라 소비 코드가 갈라짐 | 채널별로 그때그때 맞춤 파싱 | 같은 소켓 위에서 어떤 프레임은 `type` 필드로, 어떤 프레임은 특정 필드 존재 여부로 판별된다는 것. 문서가 선언한 프레임 타입과 실측 원문의 값이 어긋난 사례도 있다 |

같은 실시간 축의 두 번째 사례(NFC 출입)에서도 **브로드캐스트 + 클라이언트 필터**, **웹은 상태의
소유자가 아니라 구독자**, **유실 시 복구책이 "새로고침"뿐**이라는 같은 구조가 반복된다 `[관측]`.
다만 그쪽 엣지 클라이언트에는 "스냅샷 로드 후 스트림 소비"라는 갭 채우기 규약이 있고 웹 발권 축에는
없었다. 우리 스냅샷은 그 갭을 채울 endpoint(:8126)를 이미 선언하고 있다 `[선언]`.

## 4. 처음부터 알았다면 이렇게 설계한다

**(a) 실시간 사실은 Query 캐시에 쓰지 않는다.** 장부를 둘로 나눈다. Query 캐시는 서버가 답한 영속
사실(티켓 축)만, 화면 수명 실시간 저장소는 진행 사실(작업 축)만 소유한다. 프레임으로 목록 캐시 행을
patch하면 (1) 검색·페이지 이동으로 캐시 항목이 갈릴 때 사실이 소실되고 (2) 다음 refetch가 조용히
덮어쓰며 (3) F5·F10처럼 신뢰할 수 없는 값이 영속 장부에 들어간다. 같은 값을 두 소유자에 복제하지
않는다는 루트 원칙([AGENTS.md](../../../AGENTS.md):94-99)의 직접 적용이다.

**(b) 캐시에 손대는 것은 작업 종결 한 번뿐이다.** 종결 프레임(`DONE`/`CANCELLED`) 또는 재연결
스냅샷 수신 시 목록 query family를 invalidate한다. `CANCELLED`는 `reservationId:null`로 와서 어느 행이
바뀌었는지 말하지 않으므로, 이는 "membership·ordering을 알 수 없을 때만 family invalidate"라는 기존
조건([mutations.md](../../../.agents/skills/api-contract/references/mutations.md):8)을 그대로 만족한다.
바뀌는 것은 트리거가 mutation이 아니라 실시간 종결이라는 점뿐이다.

**(c) 귀속은 프레임 안의 식별자로만 한다.** `reservationId`가 내 세션 목록에 있으면 내 것,
없고 `issuanceJobId`가 내 세션이 채택한 job이면 내 것, 둘 다 없으면 어떤 세션에도 귀속하지 않는다.
타이밍·카운트·인덱스는 귀속 근거가 아니다. F5·F7이 구조적으로 불가능해진다.

**(d) 완료를 만들 수 있는 입력은 둘뿐이다.** 직접 받은 완료 프레임, 또는 REST 스냅샷의 티켓 상태.
`DONE`은 작업 종료이지 각 행의 성공 증거가 아니고, `ticketId` 도착은 완료가 아니며, 타이머는 아무것도
확정하지 않는다. 모르는 상태는 `확인요망`이라는 **명시적 값**이고 실패로 추정하지 않는다. F8·F9 차단.

**(e) 세션 종결은 두 조건의 AND다.** 프린터 축이 종결값이고, **잔업 지표가 해제됐을 때**만 세션을
폐기한다. 현재 잔업 해제 신호는 프레임의 `null` 카운트라는 관례뿐이므로(미확인 1) 그 판정은 서버
스냅샷이 답해야 한다. F2·F3 차단.

**(f) 구독은 앱 경계가 소유하고, 판정은 화면이 소유한다.** 연결·재구독·연결 epoch·원문 보관은 앱
수명주기이므로 app boundary가 갖는다(AGENTS.md:99). 이유는 셋이다. 같은 프린터를 여러 route(일반발권·
대량재발권·현장발권·예매상세)가 요구하고, route 전환마다 재연결하면 그 구간 프레임이 유실되며(F9의
입력), preview는 명령보다 먼저 구독돼야 늦지 않는다(구독 후 이미지 도착 약 230~260ms `[관측]`).
반대로 **어떤 프린터를 관심 대상으로 선언하는지, 세션 시작·종결, 행 상태 파생, 이탈 시 세션 폐기는
feature가 소유한다.** transport가 업무 판단을 하지 않는다는 기존 경계
([transport.md](../../../.agents/skills/api-contract/references/transport.md):7)의 실시간 판이다.
preview 구독만은 예외적으로 다이얼로그 수명에 붙는다.

**(g) 연결이 끊기면 진실은 프레임이 아니라 REST다.** 단절 구간 프레임은 복구되지 않는다. 재연결
절차는 epoch 증가 → 고정 구독 재등록 → 관심 프린터 status 재요청 → 살아 있는 job이 있으면
`GET issuance/{jobId}/status`로 예매별 상태를 다시 받아 작업 축을 재구성. epoch가 필요한 이유는 늦게
도착한 단절 이전 프레임이 새 스냅샷을 덮지 못하게 하기 위해서다. 스냅샷이 답하기 전까지는 **행이 아니라
작업 단위로** "확인 필요"를 표시하고, 사용자의 닫기·복구 행동은 막지 않는다.

**(h) 화면은 원문을 한 번만 번역한다.** 프린터 카드·행 배지·다이얼로그는 같은 파생 사실을 읽고,
각자 프레임을 다시 해석하지 않는다. F10·F11 차단.

## 5. 우리 공용 계약과의 대조

판정 넷. **커버됨** = 기존 계약이 그대로 닿는다. **수정 필요** = 계약 문장 하나를 넓히면 닿는다.
**아예 없음** = 공용 계약에 자리가 없다. **feature 소유** = 공용 계약이 이미 이 결정을 feature에
넘겼으므로 공용 결손이 아니다. 마지막 판정은 결손을 지우는 것이 아니라 **소유자를 지목**한다.

요약: **공용 결손은 세 자리다.** ① 실시간 사실(작업 축)의 상태 소유자, ② 실시간 transport
경계(연결·구독·재연결·epoch·단절 표면), ③ SSE 채널의 실제 소비. ①②는 계약의 빈자리이고 ③은
선언은 있는데 구현이 없는 자리다. 이 셋을 채우기 전에는 발권 실시간 화면을 이 레퍼런스의 계약만으로
조립할 수 없다 `[추론]`.

나머지는 결손이 아니다. 캐시 반영 한 자리는 기존 invalidate 규칙에 **트리거를 하나 더 다는 수준**이고,
행 진행·선택 잠금·연결 대기 표면·장치 strip·실행형 화면 유형 다섯은 공용 계약이 이미 feature에
넘긴 결정이다. 이 다섯을 공용 결손으로 세면 첫 화면 하나로 공용 유형을 만드는 것이 되어
promotion.md:7의 "1회 사용은 feature-local"을 정면으로 어긴다 `[추론]`.

## 6. 미확인

답이 없으면 구현이 갈리는 것만 적는다.

1. **잔업 해제를 무엇이 권위 있게 답하나.** 발생: `ERROR` 후 상태확인, 또는 종결 직후 재진입.
   기대: 세션 폐기 가능 여부와 다음 발권 착수 가능 여부. 지금은 프레임의 `null` 카운트라는 관례에만
   의존한다. 답에 따라 4(e)의 AND 조건 한쪽이 서버 필드가 되거나 화면 추정으로 남는다.
2. **완료 프레임(`ISSUING`/`ISSUED`)이 신규 서버 계약에 존재하는가.** 스냅샷에는 그 스키마가 없다.
   없다면 행 완료를 알 방법이 재연결 스냅샷 반복 호출뿐이어서 4(a)(d) 전체가 폴링 설계로 바뀐다.
3. **`printedCount`/`totalCount`의 의미와 종결 프레임에서의 보장 범위.** 발생: 진행률 표시.
   답에 따라 진행률 UI를 낼 수 있는지, 카운트를 아예 감추는지가 갈린다.
4. **동일 `ERROR` 반복이 서버 발행인가 클라이언트 이중 구독인가.** 답에 따라 멱등 처리가 표시 계층의
   책임인지 transport 계층의 책임인지 갈린다.
5. **같은 프린터를 두 운영자가 동시에 잡을 때 차단 책임이 서버인가 화면인가.** 발생: 다중 운영자 운영.
   답에 따라 발권 실행 전 preflight가 필요한지, 서버 409를 받아 처리만 하면 되는지 갈린다.
6. **실시간 연결의 인증 갱신 절차.** SSE는 access token을 쿼리 파라미터로 받는다(:10749).
   토큰 만료·재발급 시 연결을 끊고 다시 여는지, 무엇이 그 시점을 알리는지 미확인.
7. **신규 제품의 실시간 프로토콜.** 스냅샷이 선언한 실시간 채널은 SSE와 WebSocket 구독 UUID(:7849)
   둘뿐이고 STOMP 선언은 없다. 프로토콜이 달라지면 4(f)의 앱 경계 책임 범위가 달라진다.
8. **현장발권의 배포 형태(별도 창·앱)와 연결·세션 공유.**
   ([zero-sol-figma-analysis.md](../zero-sol-figma-analysis.md) §5-6과 같은 질문.)
