# Claude·Codex의 토큰 효율과 결과 품질을 함께 높이는 설계

작성일: 2026-09-14 · 대상: ZERO PLUS+ 레퍼런스 저장소와 이를 사용하는 Claude Code·Codex

문서 성격: 최초 조사 시점의 원문 분석·실측·제안 기록이다. 아래의 “미적용/후속/수행하지 않음”은 조사 당시 상태다. 후속 구현과 문서 교체의 현행 판단은 [현재 저장소 설계](../design/2026-09-14-reference-document-loop-redesign.md), 무관한 새 프로젝트 설계는 [독립 설계](../design/2026-09-14-portable-agent-document-system.md)가 소유한다. 이 연구 문서를 구현 요청의 상시 지침으로 읽지 않는다.

소유·갱신: 도입을 결정하는 프로젝트 관리자가 채택안을 기존 정본에 반영한다. 원문 도구의 동작 변경, 런타임 교체, 아래 실험 결과가 나올 때 이 문서의 판단을 재검토한다.

## 1. 먼저 읽을 결론

**가장 유망한 방향은 기존 범용 에이전트에 필요한 지식만 전달하고, 반복 작업은 검증된 코드로 실행하며, 어려운 판단에 사고 자원을 집중하는 것이다.** 도구를 많이 설치하거나 긴 사고 프롬프트를 항상 넣는 방식은 이 저장소의 우선순위가 아니다.

우선 적용할 설계는 다음 다섯 가지다. 효과 크기는 아직 실험 전이다.

1. **원문을 보존하는 선택적 문맥 전달:** 검색·인덱스로 위치를 찾고, 판단·수정 대상은 원문을 읽는다. 기존 `context`·`prepare`를 활용한다.
2. **스킬 진입점 충돌 해소:** 같은 요청에 여러 계획·승인·검증 절차가 중첩되지 않게 한다. 현재 프로젝트의 `screen-loop`를 기준으로 실제 충돌부터 다룬다.
3. **작업에 비례하는 사고:** 사소한 수정은 바로 검증하고, 어려운 설계는 대안·반례·판별 실험을 비교한다.
4. **검증된 재사용:** 이미 해결한 기계적 작업은 스크립트로 실행하고, 교훈은 근거·적용 조건과 함께 가장 가까운 정본에 반영한다.
5. **성공 작업당 비용 측정:** 압축된 문자 수뿐 아니라 전체 모델 사용량, 재읽기, 재시도, 실제 결함과 사용자의 수정 시간을 함께 센다.

Ruflo 전체 도입, 여러 메모리 엔진 동시 설치, 자동 무료 모델 전환은 **보류 권고**다. 현재 불편의 상당 부분을 기존 장치가 이미 다루고 있고, 추가 계층의 순이익은 확인되지 않았다.

## 3. 링크별 분석과 적용 판단

### 3.1 큰 파일 읽기와 “90% 절감”

대상: [These 33 Lines Cut Claude Code Token Usage by 90%](https://www.youtube.com/watch?v=_V1cjKmbJd8), Cloud Codes, 2026-09-11.

핵심 구간은 [00:54](https://www.youtube.com/watch?v=_V1cjKmbJd8&t=54)의 측정 범위, [01:59](https://www.youtube.com/watch?v=_V1cjKmbJd8&t=119)의 읽기 훅, [07:14](https://www.youtube.com/watch?v=_V1cjKmbJd8&t=434)의 반복 문맥 비용, [10:36](https://www.youtube.com/watch?v=_V1cjKmbJd8&t=636)의 RTK 반례다.

Shunt는 큰 파일의 전체 읽기를 제어하고 별도 모델에 질문을 넘긴다. 공개 벤치마크의 세 읽기 사례는 82%, 94%, 94% 절감이다. 이는 **Claude에 들어오는 해당 읽기 문맥**의 비교이며 전체 작업 토큰·청구액 절감률은 아니다. worker가 읽는 입력과 생성하는 응답도 비용에 포함해야 한다. Portal/AiKA 연결이 필요하며 단독 범용 압축기처럼 설치할 수 있는 구조는 아니다. [Shunt README](https://github.com/spotify/portal-ai-plugins/blob/main/plugins/shunt/README.md)

Spotify는 요약만으로 편집할 수 없고, 저비용 worker가 놓친 thread-safety 문제를 Claude가 발견한 사례도 공개했다. 따라서 위치 탐색과 최종 판단을 나누는 접근은 채택할 가치가 있다. [Spotify 기술 글](https://engineering.atspotify.com/2026/9/portal-by-spotify-cut-my-claude-code-token-usage-by-90)

**판단: 원리를 수정 채택하고 Shunt 직접 도입은 보류한다.** 이 저장소는 이미 절·행 단위 문맥 선택이 있다. 350줄 같은 고정 임계치를 복사하지 않는다. 긴 한국어 문단과 minified 파일은 줄 수만으로 문맥 크기를 판단할 수 없다. 필수 정본의 전체 읽기를 요구하는 현재 계약과도 충돌할 수 있다.

실제 [파일 읽기 훅](https://raw.githubusercontent.com/spotify/portal-ai-plugins/main/plugins/shunt/hooks/check-file-size)은 offset 또는 limit이 있으면 통과시킨다. [셸 읽기 훅](https://raw.githubusercontent.com/spotify/portal-ai-plugins/main/plugins/shunt/hooks/check-bash-read)은 일부 명령 이름과 파이프 문자열을 검사한다. **추론:** 모든 읽기나 실제 전달 바이트를 통제하는 장치는 아니다. `rtk` 래퍼와 다양한 실행 도구를 쓰는 이 환경에 그대로 붙여도 동일한 통제가 된다고 볼 수 없다.

### 3.3 “천재적 사고 프롬프트”

대상: [GPT로 7억 번 한국인이 공개한 미친 명령어](https://www.youtube.com/shorts/o1TucehYZuk), 2025-07-25. 자막뿐 아니라 [업로더의 고정댓글 원문](https://www.youtube.com/watch?v=o1TucehYZuk&lc=Ugx7qMJf-Zc9gPDqO7V4AaABAg)을 확인했다.

댓글은 여러 사고법 중 두 가지를 결합하고, 분석 1,500자 이상 및 아이디어 10개·3,000자 이상을 요구한다. 관찰·재정의·연결·분해는 실용적인 발상 도구다. 다만 제시된 수식은 측정 절차나 효과 검증을 제공하지 않아 지능 향상을 수치로 입증하는 근거가 되지 못한다. 수익 및 “몇 배 똑똑해진다”는 주장은 이 작업에서 검증하지 않았다.

**판단: 문제 재정의·대안 탐색·반례 검증만 수정 채택한다.** 매 요청에 긴 분량과 아이디어 수를 강제하는 부분은 제외한다. 어드민의 작은 버그에 광범위한 사업 아이디어를 생성하면 오히려 범위 이탈과 검토 비용이 생긴다. 대체 프롬프트는 §6에 제시한다.

### 3.4 “클로드가 유튜브로 공부한다”

대상: [클로드가 유튜브로 알아서 공부한다](https://www.youtube.com/shorts/kYnNTl1BWOk), 게으른빌더, 2026-09-10.

영상은 자막·영상 정보 수집, Gemini 활용, 수집 결과를 에이전트에 연결하는 흐름을 제안한다. **판단: 근거 수집 경로를 채택한다.** 이것은 현재 작업의 참고자료와 재사용 지식을 늘리는 것이며, Claude 모델 가중치를 학습시키는 절차로 볼 수 없다.

이 환경에서는 `URL → 원문 자막 → 필요한 화면 구간 → 주장별 1차 자료 → 적용 판단 → 검증된 지식` 순서를 제안한다. API·서버 계약·보안 설정은 영상만 보고 적용하지 않는다. 별도 서비스의 API 키·무료 한도·영상 지원 범위는 이번 조사에서 확인하지 않았으므로 설치 전제에 넣지 않는다.

### 3.5 Ruflo 쇼츠와 상세 가이드

대상: [지구에서 가장 좋은 클로드 사용법](https://www.youtube.com/shorts/D7S-Cl9oHz8), 2026-09-04 및 [Ruflo 입문 가이드](https://lazyowen.com/guides/ruflo), 페이지 표기 갱신일 2026-08-06.

쇼츠는 다수 에이전트, 공유 기억, 난이도별 모델 선택, 토큰 절감을 강조한다. 상세 글은 에이전트 카탈로그 숫자와 동시 실행을 구분하고, 코드가 무료여도 모델 사용료는 별개이며 역할 중복이 비용을 늘릴 수 있다고 설명한다. 판단에는 상세 설명을 우선했다.

현재 [Ruflo 공식 저장소](https://github.com/ruvnet/ruflo)는 Claude Code와 Codex를 대상으로 소개하며, 전체 초기화 시 훅·메모리·설정 등 여러 구성요소를 추가한다. 지원 표기는 확인했지만 이 프로젝트에서의 통합 실행은 검증하지 않았다.

**판단: 역할 분리와 조건부 라우팅은 채택하고 전체 설치는 보류한다.** 현재 이미 단일 편집 책임자, 독립 검토, 런타임별 훅이 있다. 별도 조정 계층을 도입하려면 기존 기능을 무엇으로 대체하고 어떤 실측 병목을 해결하는지 먼저 정해야 한다. 작은 작업에서 4~8개 에이전트도 기본값으로는 과할 수 있다. 독립 검토의 품질 이득과 총토큰 증가를 함께 측정한다.

이들 공식 자료의 기능 설명은 확인했지만 홍보 절감률, 무료 제공량, 제공사 개수는 우리 환경의 성능·예산으로 사용하지 않는다. 프록시를 조합하면 요청 경로와 실패 지점도 늘어나므로 도입 실험은 한 번에 하나씩 한다. 이는 설치 금지나 추가 승인 절차가 아니라 효과를 구분하기 위한 실험 조건이다.

### 3.7 “에이전트 대신 무엇을 만들 것인가”

대상: [Anthropic Engineer Explains: What to Build Instead of AI Agents](https://www.youtube.com/watch?v=HIRDzMtuWFk), Nate Herk, 2026-09-13.

핵심은 [01:26](https://www.youtube.com/watch?v=HIRDzMtuWFk&t=86) 검증된 스크립트 재사용, [03:03](https://www.youtube.com/watch?v=HIRDzMtuWFk&t=183) 정확한 스킬 설명, [04:56](https://www.youtube.com/watch?v=HIRDzMtuWFk&t=296) 교정을 지속 가능한 지식으로 반영, [06:43](https://www.youtube.com/watch?v=HIRDzMtuWFk&t=403) 결과물 검증이다.

**판단: 가장 넓게 채택할 방향이다.** 단, 새 프레임워크를 만들기보다 기존 스킬·스크립트·검사를 개선한다. 발표자가 제안하는 여러 페르소나의 의견은 검토 관점이며 테스트·실제 사용자 관찰과 동등한 사실 증거로 취급하지 않는다. 검토를 무조건 여러 번 반복하지 않고 새 결함이나 변경이 있을 때 다시 검증한다.

이러한 점진적 로딩과 실행 코드 재사용은 [Anthropic Agent Skills 기술 글](https://www.anthropic.com/engineering/equipping-agents-for-the-real-world-with-agent-skills)에서도 확인된다. 호환되는 형식의 이식 가능성이 서로 다른 모델의 동일한 성능을 보장하지는 않는다.

### 4.2 로컬 실측

**측정 A — 같은 체크포인트 재준비**

다음 명령을 같은 세션에서 두 번 실행했다. 두 실행 사이 체크포인트·참조 파일은 변경하지 않았다.

```sh
rtk proxy node scripts/agents/cli.mjs prepare 01a09d69-1152-7942-a1fc-69cdca4adbf5 .ai-work/agent-research/checkpoint.json
```

첫 출력은 `3 selections, 21761 bytes delivered`, 재실행은 `3 selections, 302 bytes delivered`였다. 이미 prefix에 있는 AGENTS는 첫 실행에서도 중복 출력하지 않았다. **이 사례의 재전달 바이트는 약 98.6% 감소했다.** 이는 도구가 보고한 문서 전달 부분의 바이트 비교다. 준비 호출의 모든 출력, 전체 세션 토큰, 캐시 비용, 두 모델 간 효과를 뜻하지 않는다.

**측정 B — RTK가 정본 내용을 생략하는가**

설치 버전은 `rtk 0.28.2`. Python으로 원문 bytes와 `rtk read AGENTS.md`의 stdout을 직접 비교했다.

```text
file_bytes: 25051
file_lines: 162
rtk_read_output_bytes: 9961
rtk_read_output_lines: 56
final_section_present: False
```

현재 파일의 `## 7.` 절이 출력에 포함되지 않았다. 따라서 “명령의 동작이 같으니 의사결정에 필요한 정보도 모두 보존된다”는 해석은 이 환경에서 성립하지 않는다. **RTK 규칙은 유지하되 정본·편집 대상 확인에는 `rtk proxy cat <file>` 또는 `rtk proxy sed -n '<범위>p' <file>`를 사용한다.** 원문을 부분 조회할 경우 필요한 전체 범위를 실제로 확인해야 한다. 이 방법은 이미 있는 원문 확인 지침을 사용하는 것이며 새 우회 규칙이 아니다.

**측정 C — 관련 기존 검사**

```sh
rtk proxy pnpm exec vitest run scripts/agents/preflight.test.mjs scripts/agents/context.test.mjs
```

출력: `Test Files 2 passed (2)`, `Tests 83 passed (83)`, 종료 코드 0. 문맥 선택·중복 전달·참조 검증을 다루는 기존 테스트 결과다. 제안한 새 설계의 효과나 전체 제품 품질을 입증하는 결과는 아니다.

### 4.3 지침 충돌은 토큰 문제이기도 하다

프로젝트는 범위 확정 전 `screen-loop`만 읽도록 하고, 필요한 단계만 수행한다. 이번 세션에 노출된 Superpowers의 `using-superpowers` 본문은 관련 가능성이 1%라도 있으면 읽으라는 더 넓은 진입 기준을 갖는다. 정본 위치는 `/Users/kimtaehyung/.codex/plugins/cache/openai-curated-remote/superpowers/6.3.0/skills/using-superpowers/SKILL.md`다.

현재 사용자 지침 우선순위로 적용 범위를 정할 수 있지만, 문장 자체의 적용 기준은 다르다. **추론:** 같은 요청이 여러 준비·계획·승인 절차를 유발하면 입력뿐 아니라 왕복과 중단도 늘어날 수 있다. 실제 세션별 비용 증가는 아직 측정하지 않았다.

권고는 프로젝트에서 사용할 진입 규칙을 명확히 하고, 외부 플러그인의 자동 진입을 해당 런타임의 공식 지원 방식으로 조정하는 것이다. 캐시된 플러그인 파일을 직접 고치는 방식은 업데이트 때 지속되지 않을 수 있으므로 권장하지 않는다. 규칙을 옮길 때는 기존 정본 포인터와 drift 검사도 함께 대조한다.

`AGENTS.md`는 25,051바이트, `screen-loop/SKILL.md`는 19,799바이트였다. 이 수치는 측정 시 파일 크기이며 토큰 수는 아니다. 파일 길이만으로 삭제하지 않고 실제로 겹치는 책임·불필요한 읽기 경로부터 찾는다.

## 5. 제안하는 Claude·Codex 공통 운영 구조

다음은 기존 도구 위에 적용할 작업 흐름이다. 별도 워크플로 엔진을 만들자는 제안이 아니다.

```text
요청과 성공 조건
  → 관련 스킬·정본 위치 선택
  → 검색·인덱스로 필요한 범위 찾기
  → 판단에 필요한 원문 확인
  → 작업 크기에 맞는 설계와 실행
  → 테스트·출처·실행 결과로 검증
  → 필요한 교훈만 기존 소유자에 반영
```

### 5.1 문맥은 질문에 답할 수 있을 만큼 전달한다

읽기 전에 해결할 질문을 정한다. 예를 들어 “저장 후 어느 Query key를 갱신하는가?”가 질문이면 해당 mutation과 소비 흐름을 찾는다. 전체 feature나 전체 API snapshot을 먼저 주입하지 않는다.

탐색 결과는 `질문 / 후보 파일·심볼 / 확인 근거 / 확인 못 한 범위`로 받는다. 요약 모델이 반환한 줄 번호는 탐색 힌트다. 최종 편집자는 현재 파일에서 위치와 내용을 다시 확인한다. 요약에 항목이 없다는 이유로 기능 부재를 판정하지 않는다.

기계적 검색으로 충분하면 `rg`, 기존 `context`, 타입 정의를 사용한다. 의미적 탐색량이 클 때만 범위가 독립적인 읽기 작업을 격리한다. **메인 대화 문맥 감소와 전체 에이전트 토큰 감소는 별개로 기록한다.**

이 방향은 [Anthropic 문맥 설계 글](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)의 필요한 정보만 점진적으로 찾는 접근과 부합한다. 동시에 탐색 자체가 과도해질 수 있다는 한계도 고려한다.

### 5.2 압축 여부를 정보의 역할로 결정한다

| 정보                           | 권장 처리                                                 |
| ------------------------------ | --------------------------------------------------------- |
| 명령의 반복 성공 로그·큰 목록  | 구조적으로 필터링하고 원문 위치·종료 코드 보존            |
| 대형 JSON                      | 필요한 key·조건으로 추출, 누락 여부를 판단할 때 원본 확인 |
| 규칙·권한·API 계약·편집할 코드 | 판단에 필요한 원문 보존. 요약만으로 확정하지 않음         |
| 과거 작업 기록                 | 현재 질문에 맞는 기록과 출처를 검색                       |
| 에러                           | 원인 판별에 필요한 stack·입력·실패 위치 유지              |

처음에는 출력량을 계측하고 현재 도구의 범위 선택을 활용한다. 반복적인 무차별 전체 읽기가 실측되고 대체 경로가 검증됐을 때만 훅의 제어를 검토한다. 차단 메시지 때문에 호출 수가 늘거나 정본 접근이 막히면 해당 설계를 수정한다.

### 5.3 공통 정본과 런타임 어댑터를 분리한다

| 관심사         | Claude Code                                | Codex                         | 공통 소유자                   |
| -------------- | ------------------------------------------ | ----------------------------- | ----------------------------- |
| 프로젝트 규칙  | 현재 `CLAUDE.md`가 AGENTS를 import         | AGENTS 지침 사용              | `AGENTS.md`                   |
| 업무 절차      | 현재 포인터에 따라 프로젝트 스킬 파일 읽기 | 관련 스킬 선택·읽기           | `.agents/skills`              |
| 준비·검토      | `.claude/settings.json` 훅                 | `.codex/hooks.json` 훅        | `scripts/agents/cli.mjs`      |
| 세션 간 이관   | 동일한 요구사항·근거·진행 상태 전달        | 동일                          | 기존 인계 형식·임시 작업 기록 |
| 모델·추론 수준 | 지원되는 런타임 설정에서 선택              | 지원되는 런타임 설정에서 선택 | 작업별 평가 기준              |

Codex 공식 자료는 스킬의 이름·설명을 먼저 읽고 본문을 필요할 때 불러오는 방식을 설명한다. 이는 스킬 본문을 전부 상시 주입할 필요가 없다는 근거다. [Codex 스킬 문서](https://learn.chatgpt.com/docs/build-skills) 지침의 탐색·적용 계층은 [AGENTS.md 공식 문서](https://learn.chatgpt.com/docs/agent-configuration/agents-md)로 확인한다.

Claude의 자동 발견 경로와 현재 프로젝트의 수동 파일 포인터는 같다고 가정하지 않는다. 복제 폴더를 추가하기보다 동일 파일을 읽는 현행 방식을 유지하고, 각 런타임에서 실제 읽기·훅 호출·검증 결과를 비교한다. 문서상 호환성과 실측 호환성을 구분한다.

### 5.4 기억은 세 종류만 구별한다

**현재 작업 상태:** 원래 요구사항, 사용자 수정사항, 완료·미완료, 다음 행동, 검증 결과를 기존 임시 인계에 둔다.

**제품 사실과 결정:** API·정책·권한·설계 결정은 기존 원장·ADR이 소유한다. 메모리는 위치를 찾도록 돕고 정본을 대신하지 않는다.

**반복 교훈:** 재현 조건, 실제 실패, 원인, 검증된 수정, 적용 범위, 재검토 조건을 가까운 스킬·검사에 반영한다. 코드·테스트가 이미 충분히 설명하면 같은 내용을 메모리에 다시 쓰지 않는다.

새 DB를 먼저 만들 필요는 없다. 전역 사용자 선호·프로젝트 사실·일회성 지시를 섞어 다음 프로젝트에 주입하지 않는 것이 우선이다. 자동 관찰 도구를 도입한다면 제안과 확정 규칙을 구분하며, 규칙 개선에 소비한 토큰도 측정한다.

### 5.5 스킬은 적은 수보다 정확한 진입점이 중요하다

각 스킬 설명은 다루는 결과물, 들어오는 요청, 제외 범위를 명시한다. 대표 요청마다 `명백한 양성 / 바꿔 말한 양성 / 비슷하지만 다른 음성` 사례로 테스트한다. 문자열 검사만으로 끝내지 말고 Claude와 Codex 세션에서 실제 어떤 스킬이 로드됐는지 확인한다.

프로젝트의 구현 요청은 `screen-loop`가 진입을 소유한다. API·feature·shared 계약은 범위가 정해진 후 필요한 것만 이어진다. 계획·작업·검토 스킬을 별도 의무 파이프라인으로 추가할 때는 기존 책임을 무엇으로 대체하는지 명시한다.

기존 구현과 검사로 반복 가능한 일을 새로 생성하지 않는다. 재사용 스크립트는 실제 반복이 확인됐고 입력·출력·실패 조건을 안정적으로 정할 수 있을 때 만든다. 이번 일회성 조사 스크립트를 곧바로 영구 도구로 승격하지는 않는다.

## 6. “천재적 사고”를 짧고 검증 가능하게 바꾸기

목표는 길게 생각하는 모습을 출력하는 것이 아니라 **문제를 더 잘 정의하고, 다른 대안을 찾고, 틀린 가정을 빨리 제거하는 것**이다. 다음 구분은 제안이며 현재 운영 설정에 적용하지 않았다.

| 작업                  | 사고·검증 방식                                     | 추가 에이전트                                 |
| --------------------- | -------------------------------------------------- | --------------------------------------------- |
| 명확한 카피·작은 수정 | 요구·범위 확인 → 최소 변경 → 직접 확인             | 기본적으로 불필요                             |
| 기능·상태 흐름 변경   | 연결 흐름 확인 → 소유권·실패 조건 검토 → 구현·검증 | 독립 작업이나 현재 계약의 검토 조건이 있을 때 |
| 경계·아키텍처 결정    | 현행안 포함 대안 비교 → 핵심 반례 → 판별 실험      | 독립 검토가 다른 근거를 제공할 때             |

다음은 설계 판단이 필요한 요청에 붙일 **제안 프롬프트**다. 사고 과정 전체나 최소 글자 수를 요구하지 않는다.

```text
목표와 성공 조건을 확인하고, 현재 흐름에서 결과를 제한하는 지점을 찾아주세요.
직접 확인할 수 있는 사실은 먼저 확인하고, 제품 정책은 추측하지 마세요.
설계 선택이 필요하면 현행안을 포함해 실질적으로 다른 대안을 최대 3개 비교하세요.
각 대안의 근거, 추가 복잡도, 실패 조건을 적고 가장 결정적인 반례를 확인하세요.
대안을 가르는 작은 실험이나 실제 코드·계약 검사를 수행하세요.
요구사항을 충족하는 가장 단순한 안을 선택하고, 관찰 결과로 검증하세요.
범위가 달라지면 차이를 먼저 드러내고, 기존 사용자 지시와 승인 범위를 따르세요.
출력은 결론·핵심 근거·실행 결과·미확인만 작업 크기에 맞게 작성하세요.
```

단순 작업에 대안 세 개를 억지로 만들 필요는 없다. 위 프롬프트도 매번 루트에 추가할 상시 문구가 아니라 기존 설계 단계의 표현을 개선할 때 사용할 후보이다.

**이 프로젝트에 적용한 사고 예시**

문제 “토큰을 줄이자”를 “같은 요구사항을 더 적은 재탐색·재작업으로 검증 가능하게 처리하자”로 구체화했다. 후보는 기존 문맥 선택 개선, 압축 프록시 도입, 대규모 위임이다. 이번 원문 누락 실측은 무조건 압축하는 안의 반례이고, 재준비 전달량 실측은 기존 장치를 활용할 근거다. 따라서 1차 선택은 **기존 선택 전달 활용 + 원문 보존 + 진입 충돌 정리**다. 총비용 우위는 §8의 실험으로 판별한다.

이는 이번 자료를 종합한 판단이다. “천재적”이라는 자기평가나 검증하지 않은 A급 판정은 하지 않는다.

## 8. 토큰과 품질을 검증하는 방법

### 8.1 같은 이름의 “절감률”을 분리한다

| 측정값              | 알려주는 것                   | 알려주지 못하는 것               |
| ------------------- | ----------------------------- | -------------------------------- |
| 출력 바이트 감소    | 도구 결과가 얼마나 작아졌는가 | 실제 토큰·청구액·정보 보존       |
| 메인 입력 토큰 감소 | 주 모델에 전달한 양           | worker·재시도까지 포함한 총량    |
| 캐시 입력 비율      | 반복 입력의 캐시 활용         | 반복 입력이 무료인지 여부        |
| 전체 모델 비용      | 모델별 사용료의 합            | 사용자의 재작업 시간·품질        |
| 통과 작업당 비용    | 요구사항을 만족한 결과의 효율 | 측정하지 않은 실제 운영 시나리오 |

OpenAI의 prompt caching은 반복되는 prefix에 적용되며, 안정적인 공통 부분과 요청마다 바뀌는 내용을 배치하는 방식이 중요하다. 캐시로 비용이 줄어도 문맥 자체가 사라지는 것은 아니다. [OpenAI Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching)

Claude 공식 문서도 문맥 크기·캐시·다중 에이전트 비용을 구분하고 스킬의 필요시 로딩을 권장한다. [Claude 비용 관리](https://code.claude.com/docs/en/costs) API 단가로 계산한 비용을 구독 한도와 동일하게 환산하지 않는다.

JetBrains의 특정 paired 실험은 RTK 사용 시 low effort에서 작업당 비용 중앙값이 7.6% 증가했고, high effort에서는 뚜렷한 이득이 없었다고 보고한다. 이는 지정된 버전·모델·벤치마크의 결과이며 모든 RTK 사용의 결론이 아니다. 현재 설치 버전과도 다르다. 그래도 **압축률만으로 총비용 절감을 단정할 수 없다는 직접 반례**다. [JetBrains 실험](https://blog.jetbrains.com/ai/2026/07/rtk-claude-code-token-savings/)

### 8.2 작은 파일럿을 먼저 수행한다

**제안 실험 규모:** 실제 프로젝트의 서로 다른 작업 6개를 고른다. 작은 수정 2개, 연결 상태 흐름 수정 2개, 근거 탐색·설계 판단 2개다. 각 작업을 기준선/개선안으로 최소 2쌍 반복한다. 한 런타임당 24회, 양쪽을 비교하면 48회이므로 우선 한 런타임에서 파일럿을 하고 가치가 확인되면 확대한다. 이번에는 이 모델 호출 실험을 실행하지 않았다.

동일 커밋·작업·모델·추론 설정·권한·도구 버전을 고정한다. 개선할 한 요소만 바꾼다. 순서 효과를 줄이기 위해 실행 순서를 바꾸고, 새 세션의 cold 조건과 warm-cache 조건을 분리해 기록한다. 이전 실행의 정답·수정 diff·자동 기억이 다른 arm으로 새어 들어가지 않도록 독립 환경을 사용한다.

| 작업 ID            | 런타임·모델·effort | 개선 요소   | 입력·캐시·출력 | worker·재시도 포함 비용 | 벽시계 시간 | 원문 재조회 | 최종 통과       | 사용자 수정 분 |
| ------------------ | ------------------ | ----------- | -------------- | ----------------------- | ----------- | ----------- | --------------- | -------------- |
| 실제 작업으로 채움 | 버전 고정          | 하나만 변경 | 실제 usage     | 실제 usage 또는 미확인  | 실행 기록   | 횟수·이유   | 요구사항별 검증 | 후속 관찰      |

가격 계산은 실제 모델·제공사별 usage 분류를 사용한다. cache write/read·추론 토큰이 별도인지 포함인지 확인하고 중복 합산하지 않는다. 호출·기억 요약·embedding 등 부가비용도 발생했다면 포함한다. usage를 제공하지 않는 런타임에서는 `측정 불가`로 기록하고 문자 수로 청구액을 만들어 내지 않는다.

주 지표는 **각 arm에서 실패·재시도까지 소비한 전체 비용 ÷ 최종 기준을 통과한 작업 수**다. 실패한 실행을 비용에서 빼지 않는다. 작업별 결과와 전체 합계, 사용자 수정 시간도 함께 본다.

**도입 판정 제안:** 필수 시나리오 누락과 새 중대 결함이 없고, 원문 오독·요약 누락이 늘지 않으며, 성공 작업당 비용 또는 사용자 수정 시간이 개선돼야 한다. 예를 들어 비용 15% 감소를 실험 전에 목표로 정할 수 있지만 이는 보장치가 아니다. 작은 파일럿 결과는 경향으로 보고, 효과가 작거나 편차가 크면 반복 수를 늘린다.

정보 누락, 불필요한 재질문, 동일 파일 재읽기, 검토 루프 증가가 나타나면 해당 조건의 압축·위임을 제거하거나 조정한다. “실행됐음”과 “쓸 가치가 있음”을 구분한다.

## 9. 최종 판단과 남은 검증

**채택할 핵심은 선택적 문맥, 원문 기반 판단, 검증된 실행 코드, 짧은 대안·반례 비교, 근거를 가진 교훈 축적이다.** 현재 저장소는 그 상당 부분을 이미 갖고 있다. 다음 개선의 우선순위는 새 도구 추가보다 기존 규칙의 실제 준수와 불필요한 중복 진입을 줄이는 데 있다.

확인된 것은 링크의 자막·본문·고정댓글, 연결된 공식 자료의 해당 기능 설명, 로컬 문맥 전달량, RTK 출력 누락, 관련 테스트 83개 통과다. 제안한 설계의 품질·총토큰·청구액 개선률은 미확인이다. Claude 런타임 실측, 새 도구 통합, A/B 작업 실험이 남았다. 이들 미확인은 보고서 작성의 차단 조건은 아니지만 실제 도입 효과를 확정하는 조건이다.

영구 변경 파일은 이 문서 한 개다. 조사 원문·체크포인트·검토 기록은 `.ai-work/agent-research/`에 두어 운영 지침의 상시 입력으로 만들지 않았다. 작업 시작 때 존재한 `v3-debug.png`는 수정하지 않았다.
